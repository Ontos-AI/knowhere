# Word 公式与嵌入对象处理方案（代码级）

日期：2026-11-21　范围：Knowhere worker 的 Word（DOCX）精解析，即 `iter_block_items` → `parse_docx` 这条路径。粗解析（LibreOffice 转 PDF 取文字）不改。

## 1. 目标

1. **新式公式**（Word 自带公式编辑器，存成 OMML）转成 LaTeX，放回原文位置。现在这些公式在正文和表格里都被整段丢掉。
2. **老式公式**（Equation 3.0 / MathType 嵌入对象）先不转换内容，只在原位置留一个标记，让读者知道这里有公式。
3. **其他嵌入对象**（Photoshop、Visio、画图、AutoCAD 等）转成 PNG 图片，放回原位置。
4. **表格单元格里的旧格式图、嵌入对象和公式**，按正文同样的规则处理。

不改的地方：
- 粗解析阶段；
- 普通图片（DrawingML）的提取；
- 标题识别算法本身；
- 图片描述、去重、上传流程；
- 表格转 HTML 的结构逻辑（合并单元格、嵌套表格）。

## 2. 现状（用本地 996 个 Word 文件实测）

| 类型 | 数量 | 所在文件 | 正文 / 表格 | 现在的结果 |
|---|---|---|---|---|
| 新式公式（OMML） | 1358 处（独占一行的 60 处，嵌在句中的 1298 处） | 43 个 | 1302 / 56 | 文字取不到，整段公式消失；只有公式的段落整段被跳过 |
| 老式公式（`Equation.3`、`Equation.DSMT4`） | 513 处 | 4 个 | 215 / 298 | 正文里没有文字的段落会出现 `[VML graphic — extraction not yet supported]`；有文字的段落和表格里则什么都不留 |
| Photoshop 对象 | 407 处 | 37 个 | 全在正文 | 同上 |
| Visio 对象 | 17 处 | 2 个 | 13 / 4 | 同上 |
| 画图（PBrush） | 2 处 | 2 个 | 正文 | 同上 |
| AutoCAD 对象 | 1 处 | 1 个 | 正文 | 同上 |
| 表格里的 VML 叠加图 / 单张 VML 图 | 各 1 处 | 2 个 | 表格 | 跳过 |

原因（已对照代码确认）：
- 正文和表格的文字都来自读 Word 用的第三方库 python-docx（1.2.0）。它取段落文字的写法是 `"".join(e.text for e in self.xpath("w:r | w:hyperlink"))`，只读普通文字块，公式（`m:oMath`）不在其中。`parse_docx` 里的 `block.text`、表格的 `cell.text` 都走这条路。
- 嵌入对象（`w:object`）在文件里只存了一张 WMF/EMF 格式的预览图。现在的代码不认识它，只因为它里面有 `v:imagedata`，就触发了旧的占位提示。
- 表格单元格只提取普通图片（`a:blip`），代码注释写明“VML images in cells are skipped”。

**嵌入对象能否画出来（已实测）**：用上一个提交里给 VML 叠加图写的批量渲染流程试了 4 个文件，选中的对象全部画出来了：

| 文件 | 画出来 / 选中 | 耗时 |
|---|---|---|
| 模板施工方案 | 2 / 2 | 3.0 秒 |
| 云边端论文 | 6 / 6 | 7.2 秒 |
| PRE 招标文件 | 6 / 6 | 6.3 秒 |
| 机房投标文件 | 1 / 1 | 2.1 秒 |

逐张看过：Visio 流程图、AutoCAD 大样图、Photoshop 表单、论文架构图都清晰完整。

## 3. 统一原则

1. **只在精解析阶段处理**。直接读 Word 原始数据，每个公式、对象都在它原来的位置被找到，处理完放回原位。
2. **能变成文字的就给文字，不能的才给图**：
   - 新式公式给 LaTeX，能被搜索；
   - 老式公式只给位置标记；
   - 其他嵌入对象、VML 叠加图给图片。
3. **只有一种渲染方式**：需要“画出来”的东西（VML 叠加图、嵌入对象）都走现有的批量渲染。每个文件只调用一次 LibreOffice，按实际画出的范围裁剪，不另起第二套转换。每个对象前面加一页编号页，按编号认领结果（4.4）。
4. **正文、内容控件、表格共用同一套规则**：
   - 取文字统一用一个函数；
   - 找图统一用一套规则。
   - 三处入口不再各写各的。
5. **标记写给 Agent 看**：取不到内容的地方，用固定的英文方括号标记写清“这里有什么、为什么没有内容”，让 Agent 知道原文这里有东西，不去猜。

## 4. 改动清单

### 4.1 段落文字：新增 `paragraph_text`（新文件 `formats/docx/paragraph_text.py`）

`paragraph_text(paragraph) -> str`。按段落子元素的原有顺序拼文字：
- `w:r`、`w:hyperlink`：用 python-docx 自己的 `.text`，和现在完全一样。制表符、换行的处理也保持不变。
- 文字块里如果有老式公式对象：在该文字块的文字后面加上老式公式标记 `[equation not extracted]`（4.3）。
- `m:oMath`：放 `$` + LaTeX + `$`，见 4.2。
- `m:oMathPara`：独占一行的公式。其中每个 `m:oMath` 放 `$$` + LaTeX + `$$`，前后用换行和正文隔开。
- 其他子元素：和现在一样忽略。

接入点（全部换成这个函数，之后不再有第二种取段落文字的写法）：

| 位置 | 现在 | 改后 |
|---|---|---|
| `parser.py` `parse_docx` 标题候选 | `block.text` | `paragraph_text(block)` |
| `parser.py` `parse_docx` 正文 `PTXT` | `getattr(block, "text", ...)` | `paragraph_text(block)` |
| `table_html.py` 单元格内容 | `cell.text` | 单元格各段落的 `paragraph_text` 用 `\n` 连接（和 python-docx `cell.text` 的连接方式一致） |
| `parser.py` `_first_cols_rows`（表格摘要用的首行首列） | `cell.text` | 同上 |
| `block_stream.py` 正文段落的 `text`（决定是否产出段落、是否加占位） | `.//w:t` | `paragraph_text` |
| `block_stream.py` 内容控件（`w:sdt`）段落 | 产出 `.//w:t` 拼成的字符串 | 产出 python-docx 段落对象，文字由 `paragraph_text` 取 |

关于内容控件这一行，需要说明一个行为变化：
- 现在内容控件里每个 `w:p`（包括文本框里的段落）都会单独读一遍，外层段落又用 `.//w:t` 把文本框里的字再读一遍，所以文本框文字会重复。
- 改成按 python-docx 的规则取文字后，外层段落不再包含文本框里的字。文本框段落自己仍然会被读到，所以文字不会丢，只是去掉了重复。
- 内容控件里的段落要拿到 python-docx 的段落对象，做法和现在正文段落一样：用 python-docx 解析出的 body 子元素和 lxml 解析出的 body 子元素一一对应（现有 `p_tbl_map` 就是这样对应的），把这种对应从“段落 / 表格”扩展到内容控件。

### 4.2 OMML → LaTeX 转换器（新文件 `formats/docx/omml_latex.py`）

`omml_to_latex(o_math) -> str`。按 ECMA-376 第 1 部分 22.1 节定义的公式结构递归转换：

| OMML 元素 | LaTeX | 样本中出现次数 |
|---|---|---|
| `r` / `t` 文字 | 原文字，转义 LaTeX 特殊字符 `\ { } _ ^ % # & $` | 10811 |
| `sSub` / `sSup` / `sSubSup` | `x_{..}` / `x^{..}` / `x_{..}^{..}` | 2511 / 171 / 548 |
| `d` 括号（`begChr` / `endChr` / `sepChr`） | `\left( .. \right)`，分隔符按 `sepChr` 写 | 371 |
| `f` 分数 | `\frac{..}{..}` | 209 |
| `acc` 重音 | `\hat` / `\tilde` / `\bar` / `\vec` / `\dot` 等，按 `chr` 对应 | 154 |
| `nary` 求和、积分类 | `\sum` / `\prod` / `\int` / `\oint` 等，按 `chr` 对应，带上下限 | 91 |
| `eqArr` 多行方程 | `\begin{aligned} .. \end{aligned}`，行间用 `\\` | 26 |
| `func` / `fName` 函数名 | `\operatorname{..}` + 参数 | 8 |
| `rad` 根号（`deg` 次数） | `\sqrt{..}` / `\sqrt[n]{..}` | 3 |
| `borderBox` 加框 | `\boxed{..}` | 3 |
| `limLow` / `limUpp` 上下极限 | `\underset{..}{..}` / `\overset{..}{..}` | 1 / 0 |
| `m` 矩阵、`groupChr`、`bar`、`box`、`sPre`、`phant` | `\begin{matrix}`、`\underbrace` / `\overbrace`、`\overline` / `\underline`、原样、`{}_{..}^{..}x`、原样 | 样本中没有，按规范补齐 |
| 其他不认识的元素 | 只取其中的文字，不丢内容 | — |

说明：
- 字符对应表（`nary`、`acc`、`groupChr` 的 `chr`，以及 `d` 的括号字符）只收录规范里列出的默认值和常见值。没收录的字符原样输出，不报错，也不丢弃。
- 样式属性（`sty`、`scr`、`nor`）不影响内容，第一版不转成 `\mathbf`、`\mathcal` 之类，只保留文字。
- 不引入外部库，自己写（第 5 节决策 1）。

### 4.3 老式公式：只留位置标记

- 判断方法：`w:object` 下的 `o:OLEObject` 的 `ProgID` 以 `Equation.` 开头。样本里只有 `Equation.3` 和 `Equation.DSMT4` 两种，都符合。
- 处理方式：由 `paragraph_text` 在原位置写固定标记 `[equation not extracted]`，不提取预览图，也不交给渲染。
- 标记直接嵌在句子里，例如 `系数取 [equation not extracted]，其中 k 为……`。Agent 能看出公式在句中的哪个位置，也知道内容没取到，需要时会去看原文。
- 表格单元格里的老式公式同样经过 `paragraph_text`，标记会出现在单元格文字里。

### 4.4 嵌入对象：并入现有渲染（改 `vml_graphics.py`，改名为 `legacy_graphics.py`）

“需要画出来的东西”从“VML 叠加图”扩展为两类：
- VML 叠加图：含 `v:group` 的最外层 `w:pict`；
- 非公式嵌入对象：`ProgID` 不以 `Equation.` 开头的 `w:object`，包括没有 `ProgID` 的。

筛选规则沿用现有写法：
- 不在 `mc:Fallback` 里；
- 不嵌套在另一个 `w:pict` 里。

**按编号页认领**（替换现在“按页数对号”的做法）：
- 现在的做法：每个对象占一页，转完后要求总页数正好等于对象数，然后按顺序对号。只要有一个对象挤成两页，页数就对不上，整份文件的渲染结果全部放弃。
- 改后：临时文件里每个对象前面加一页编号页，编号页上只有一行固定格式的编号文字（例如 `knowhere-render-mark-7`，前缀是模块里的常量）。转成 PDF 后，用 PyMuPDF 读每页文字：
  - 一页的文字正好等于某个编号，它就是编号页；
  - 从这个编号页到下一个编号页之间的页面，都属于这个编号的对象。
- 认领结果：
  - 一个对象正常占一页：裁剪后得到一张图，和现在一样。
  - 一个对象挤成了多页：每一页有内容的都裁剪出来，按顺序作为同一个对象的多张图放回，不截断。
  - 一个对象的页面全是空白：只有它退回占位，不影响其他对象。
  - 编号页缺失或顺序不对（说明转换本身出了问题）：这份文件的渲染结果全部放弃，退回占位，并记一条警告日志。
- 代价：临时文件页数翻倍。编号页只有一行字，不画图，增加的时间很少。验证时会和现在的耗时对比。

裁剪规则不变。

重命名：
- 生成的图片名从 `vml-composite-{n}.png` 改成 `rendered-graphic-{n}.png`。一个对象出了多张图时，名字为 `rendered-graphic-{n}-{k}.png`；
- 函数名中的 composite 改为 rendered graphic；
- 模块说明里写清楚这两类对象。

单张 VML 图（只引用一个现成图片文件）仍然直接读文件，不渲染。

### 4.5 表格单元格（改 `block_stream.py` 表格分支）

- 渲染前的统一收集从“正文段落、内容控件段落”扩展到表格单元格。每个文件仍然只调用一次 LibreOffice。
- 每个单元格按顺序取：
  1. 普通图片（现有）；
  2. 单张 VML 图（直接读文件）；
  3. 需要渲染的对象（按位置查渲染结果）。
- 结果放进现有的 `cell_images[(行, 列)]`，后面的保存、描述、去重、表格内图片编号全部复用现有 `handle_table` 流程，不改。
- 单元格里画不出来的对象：和现在一样什么都不放，不加占位。表格里本来就没有占位提示，这一点不变。
- 正文和表格共用一个取图函数（就是现在的 `_paragraph_images` 里的取图部分），不再在表格分支里另写一份 `a:blip` 读取逻辑。

### 4.6 画出来的图也按尺寸过滤

- 画出来的图和普通图片用同一条规则：小于 `ProcessingConstants.IMG_MIN_SIZE`（10KB）的不要，调用现有的 `is_below_img_min_size`。
- 被过滤掉的图视为“已处理”，不加占位，和普通小图一样。
- 在过滤的位置加 TODO 注释，写明：画出来的图里可能有信息量很大但文件很小的线条图（例如安全报告里约 9KB 的雷达图碎片），现在会被一起去掉，之后需要单独评估画出来的图该用什么过滤规则。

### 4.7 占位提示

- 现在的触发条件是“段落里有 `v:group` 或 `v:imagedata`”，嵌入对象也会触发。
- 改为：只在段落里存在“应该画出来、但渲染失败”的对象时才加占位。也就是说，老式公式（已有标记）、画出来的对象、单张 VML 图都不再触发。
- 提示文字从 `[VML graphic — extraction not yet supported]` 改为 `[graphic not extracted]`。如果是嵌入对象，就带上它在文件里登记的类型名，例如 `[graphic not extracted: Visio.Drawing.11]`，让 Agent 知道原文这里是什么东西。类型名直接用文件里的 `ProgID` 原文，不另建对应表。

### 4.8 不改

- 粗解析（`docx_baseline`）；
- 普通图片读取；
- 图片尺寸过滤规则本身；
- 标题识别算法；
- 表格转 HTML 的结构逻辑；
- 已有的嵌套表格行号计算方式（`.//w:tr` 会把嵌套表格的行也数进去）。

最后这一条是现有问题，单独记录，不在本次范围。

## 5. 已定决策（2026-11-21）

| # | 问题 | 决定 | 理由 |
|---|---|---|---|
| 1 | 公式转换用什么 | 自己写（4.2），不新增依赖 | Python 里能找到的 OMML 转换库大多多年没维护；pandoc 需要额外装二进制程序 |
| 2 | LaTeX 在文字里的写法 | 句中公式 `$...$`；独占一行的公式 `$$...$$`，单独成行 | 这是 Markdown 里写数学公式最通用的约定，Agent 和常见的公式显示组件（KaTeX、MathJax）都直接认。区分两种写法能保留“这是行内符号还是一条独立方程”的信息。Knowhere 目前没有别处输出公式（MinerU 的公式识别是关着的），所以不存在和别的格式对齐的问题。标题识别已有规则会把 `$...\命令...$` 这类行判为非标题 |
| 3 | 标记文字 | 老式公式写 `[equation not extracted]`；渲染失败写 `[graphic not extracted]`，嵌入对象再带上类型名，例如 `[graphic not extracted: Visio.Drawing.11]` | 英文方括号短标记，中英文文档都通用，和原有占位风格一致。说清了“是什么”和“没取到”，Agent 不会把它当正文，也不会去猜内容 |
| 4 | 画出来的图是否按 10KB 过滤 | 暂时过滤，加 TODO 注释（4.6） | 和普通图片同一条规则；小线条图可能被误删，留作后续评估 |

## 6. 风险

1. **对象跨页**：改成按编号页认领后，一个对象跨页只影响它自己，并且不截断（4.4）。只有编号页本身缺失或顺序不对时，才会整份退回占位。验证时统计 996 个文件里跨页对象和整份退回的数量。
2. **公式文字会改变内容哈希**：含公式的文件重新解析后，段落内容变了，`know_id` 也会跟着变。属于正常的重新解析结果。
3. **公式被识别成标题**：现在公式段落是空的，不会成为标题候选。加上 LaTeX 后会进入候选。标题识别里已有规则把含 `\times`、`\frac` 这类写法的行判为非标题（`heading_candidates.py`），验证时会对比 996 个文件改动前后的标题数量。
4. **显示依赖读的一方**：`$...$` 对 Agent 和检索是普通文字，能直接理解。在 Hipo 网页上能不能显示成数学公式，取决于前端是否渲染 LaTeX，不在本方案范围。
5. **耗时**：嵌入对象多的文件，精解析会多 2 到 7 秒（一次 LibreOffice 调用）。没有对象的文件不受影响。

实现中对方案的补充和解释：
1. 每个没画出来的图形各留一处占位，不再看段落有没有文字。旧代码那种由 `mc:Fallback` 里的 VML 备份触发的占位（例如 WPS 模板里的装饰线条）随之消失，这些图形的 DrawingML 原件已经读过。
2. 修订：解析前先接受全部修订（见 8.1），公式代码里不再单独判断修订。整条公式没有内容时不输出任何东西（否则会留下空的 `$$`）。
3. 新式公式里嵌着的老式公式对象（WPS 公式编辑器），也在公式后标出位置。
4. 公式文字中对 LaTeX 有特殊含义的字符会转义。上下标、根号等的底数统一加花括号。不认识的重音写成 `\overset`。`\left`/`\right` 不支持的括号原样输出。
5. 内容控件里的段落改为输出 Paragraph 对象，和正文段落一样参与标题识别。正文段落一定有对应的 Paragraph 对象，不再输出纯文字。
6. 表格单元格文字和标题判断都统一走 `cell_text` / `paragraph_text`。

### 8.1 修订记录：解析前接受全部修订（2026-11-21 追加，已确认）

问题：修订记录在多处进入了解析。
- 修订插入的文字读不到（python-docx 本来就不读）。
- 修订删除的图片、嵌入对象仍会被提取或渲染。
- 被删的表格行成了空行。
- 整篇转 PDF 时，删掉的文字仍印在页面上。
- 公式里被删的结构留下 `{}_{}` 这样的空架子。

做法：新文件 `formats/docx/tracked_changes.py`，`accept_tracked_changes(package_bytes)` 按 Word 的规则（ECMA-376 第 1 部分 17.13.5）接受文件里所有 WordprocessingML 部件（正文、页眉页脚、脚注等）的修订：
- 删除、移走的内容去掉；插入、移入的内容作为普通内容保留。
- 段落标记被删的段落并入下一段，用下一段的段落属性；后面没有可并入的段落时原地保留。
- 被删的表格行去掉，行删光的表格一起去掉；被删的单元格去掉。
- 公式结构自己的控制符（如 `m:sSubPr/m:ctrlPr`）带删除标记时，整个结构连同参数去掉。这就是空架子的通用处理：依据 Word 自己的删除标记，不靠猜。
- 格式修改前的旧格式记录（`*PrChange`）和移动范围标记丢掉。
- 没有修订的文件原样返回，不重写。

接入点（之后所有读取都只看定稿版）：
- `word_package.read_word_package_bytes`：先规范内容类型，再接受修订。`iter_block_items`（精解析、对象渲染）和 `open_word_document`（页数估算）都用它。
- `baseline.parse_docx_baseline`：整篇转 PDF 前先接受修订，写到临时目录再交给 LibreOffice。页面图和页面文字都是定稿版。
- `omml_latex` 和 `paragraph_text` 里原来跳过删除内容的判断已删除。

未处理：单元格合并的修订（`w:cellMerge`）。样本里没有出现，规范含义也无法用样本验证，保持原样。

真实数据（996 个文件，对比上一提交）：
