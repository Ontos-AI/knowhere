# OpenSearch remote-store durability research

Date: 2026-11-02. Status: **research and validation recommendation; not an accepted production design**.

## Scope and conclusion

The candidate is one private us-east-1 Linux ARM64 `r7g.xlarge` (4 vCPU, 32 GiB RAM, 16 GiB heap), encrypted 100 GiB gp3 data volume (3,000 IOPS, 125 MiB/s), 20 GiB root volume, one primary per owner and namespace, zero replicas, and idle indexes closed by Knowhere. There are approximately 370 namespaces, mostly below 50 units, with the largest around 45,000. Lexical input is jieba-pretokenized whitespace text using BM25. These are supplied validation assumptions, not sizing conclusions.

**Recommend validating remote segments + request-durable remote translogs + remote cluster state, alongside independent full S3 snapshots.** This supplies an OpenSearch-owned candidate recovery path for acknowledged writes after the only node and its EBS volume are lost. The official durability statement is conditional on `index.translog.durability=request`, and explicitly applies regardless of replica count. It does not promise uninterrupted service or protection against every logical mistake. [Remote-backed storage](https://docs.opensearch.org/latest/tuning-your-cluster/availability-and-recovery/remote-store/index/)

PostgreSQL is excluded as a lexical runtime fallback, persistent lexical backup, post-snapshot replay source, and disaster-recovery regeneration source. Old PostgreSQL lexical writes and derived data will stop/be deleted after migration validation. Canonical bodies, vectors, and normal application metadata may remain there but are **not recovery data for this proposal**. The earlier four-hour PostgreSQL rebuild proposal is withdrawn. Healthy-volume recovery within 15 minutes and snapshot recovery within one hour remain unverified internal targets.

Research used current official documentation and the official **3.9.0 tag, commit `4ee42a94e87f66fbf1e62a9871b1b87f91e02472`**. Production version selection remains open; the prior 3.9.0 visibility probe did not validate durability. Source conclusions below are pinned to that tag, not `main`, Amazon OpenSearch Service, or Serverless. [Pinned source](https://github.com/opensearch-project/OpenSearch/tree/3.9.0)

## Acknowledgment and failure boundary

| Configuration | What the evidence supports |
| --- | --- |
| Local translog, `request` | Fsync/commit before successful acknowledgment protects against process/node crashes while the durable disk survives. This alone cannot recover a destroyed only disk. |
| Remote store, `async` | Background persistence permits acknowledgment before remote sync; outstanding acknowledged operations can be lost. Do not interpret a configured interval as a guaranteed maximum loss window under upload failures. |
| Remote store, `request` | Document operations are acknowledged after required translog synchronization; remote storage is the candidate surviving copy when the only local disk is lost. |

`request`, **not `async`**, is the default in both documentation and 3.9.0 `IndexSettings`. Explicitly pin it rather than depending on defaults. The pinned write action waits for its sync callback, propagating sync failure; remote translog synchronization uploads data/checkpoint files and then transfer metadata, and upload failures propagate through its listener. [Index settings](https://docs.opensearch.org/latest/install-and-configure/configuring-opensearch/index-settings/), [3.9.0 default](https://github.com/opensearch-project/OpenSearch/blob/3.9.0/server/src/main/java/org/opensearch/index/IndexSettings.java#L194-L200), [write response gate](https://github.com/opensearch-project/OpenSearch/blob/3.9.0/server/src/main/java/org/opensearch/action/support/replication/TransportWriteAction.java#L503-L547), [remote synchronization](https://github.com/opensearch-project/OpenSearch/blob/3.9.0/server/src/main/java/org/opensearch/index/translog/RemoteFsTranslog.java#L533-L646), [upload failure propagation](https://github.com/opensearch-project/OpenSearch/blob/3.9.0/server/src/main/java/org/opensearch/index/translog/RemoteFsTranslog.java#L956-L964)

An asynchronous I/O implementation or `remote_store.translog.buffer_interval` can batch pending sync work without changing the `request` acknowledgment gate. It must not be described as inherently asynchronous durability. The optional static `cluster.remote_store.index.restrict.async-durability=true` rejects creation/modification of indexes using `async`; its default is false. [Buffered sync processor](https://github.com/opensearch-project/OpenSearch/blob/3.9.0/server/src/main/java/org/opensearch/index/shard/IndexShard.java#L5409-L5449), [restriction setting](https://github.com/opensearch-project/OpenSearch/blob/3.9.0/server/src/main/java/org/opensearch/indices/IndicesService.java#L373-L383)

Index/create, update, and document-delete outcomes must be checked individually. Bulk actions are independent: HTTP success for the envelope is not success for every item. A timeout/disconnection leaves the client uncertain whether an operation committed; recovery validation must distinguish recorded successful items from ambiguous outcomes. `refresh=wait_for` controls search visibility, not remote durability. [Bulk API](https://docs.opensearch.org/latest/api-reference/document-apis/bulk/)

## Three different remote components

| Component | Purpose |
| --- | --- |
| Segment repository | Stores Lucene segment files produced through refresh/flush/merge; replicas can download them. Segments alone do not establish the latest acknowledged-write boundary. |
| Translog repository | Preserves operations needed beyond the available segment commit; request durability closes the periodic-snapshot gap for document operations. |
| Cluster-state repository | Preserves index identities, settings, mappings, and global metadata needed to find and interpret the data. It is enabled separately from remote data. |

Remote store requires segment replication, supports S3 through the repository interface, and can use one repository for these components. All nodes must have matching repository attributes. Repository attributes alone do not enable remote cluster state: configure `cluster.remote_store.state.enabled=true`. [Remote-store architecture and configuration](https://docs.opensearch.org/latest/tuning-your-cluster/availability-and-recovery/remote-store/index/), [remote cluster state](https://docs.opensearch.org/latest/tuning-your-cluster/availability-and-recovery/remote-store/remote-cluster-state/)

**Remote state versus remote publication:** in 3.9.0, state-enabled coordination writes remote state before publishing, and writes its committed form before sending commit requests. These gates depend on state enablement, not on `cluster.remote_store.publication.enabled`. The latter changes publication transport so followers download state remotely; it is not an additional prerequisite for the basic remote metadata durability path. Treat successful committed metadata updates separately from document acknowledgments and unacknowledged/in-flight changes. [Pre-publication/pre-commit gates](https://github.com/opensearch-project/OpenSearch/blob/3.9.0/server/src/main/java/org/opensearch/cluster/coordination/CoordinationState.java#L579-L598), [publication ordering](https://github.com/opensearch-project/OpenSearch/blob/3.9.0/server/src/main/java/org/opensearch/cluster/coordination/Coordinator.java#L1414-L1428), [commit ordering](https://github.com/opensearch-project/OpenSearch/blob/3.9.0/server/src/main/java/org/opensearch/cluster/coordination/CoordinationState.java#L499-L511)

## Losing the entire only node and disk

The supported mechanism does not require a surviving old node, but it does require recoverable remote metadata and an independently reproducible installation/configuration:

1. Fence the old instance and prevent concurrent writers to the same live repositories. Provision a clean replacement with the selected version, plugins, security material, and repository access.
2. Supply the original `cluster.name`, remote repository names/buckets/base paths/regions, state enablement, and valid discovery/bootstrap configuration. With an unknown local cluster UUID, 3.9.0 startup discovers the latest valid remote UUID chain by cluster name and restores metadata. No valid remote chain can instead leave startup with empty initial state; a running empty replacement is not recovery success. [Startup selection](https://github.com/opensearch-project/OpenSearch/blob/3.9.0/server/src/main/java/org/opensearch/gateway/GatewayMetaState.java#L165-L187), [UUID-chain validation](https://github.com/opensearch-project/OpenSearch/blob/3.9.0/server/src/main/java/org/opensearch/gateway/remote/RemoteClusterStateService.java#L1941-L2031)
3. Expect a **new cluster UUID**, with restored index/global metadata. The official full-cluster integration test replaces all nodes, asserts the changed UUID, verifies metadata, then observes red indexes and invokes remote-store restoration. Automatic metadata bootstrapping does not itself prove completed shard recovery. [Full replacement test](https://github.com/opensearch-project/OpenSearch/blob/3.9.0/server/src/internalClusterTest/java/org/opensearch/remotestore/RemoteStoreClusterStateRestoreIT.java#L94-L191)
4. Restore unavailable primaries using `POST /_remotestore/_restore`, then verify recovered content and new writes. The ordinary REST path works from **existing cluster index metadata**; it cannot reconstruct a deleted/missing index merely from arbitrary remote objects. `restore_all_shards=true` requires the existing index to be closed and reopens it. Preserve/test the normal idle-closed-index lifecycle separately. [Restore implementation](https://github.com/opensearch-project/OpenSearch/blob/3.9.0/server/src/main/java/org/opensearch/index/recovery/RemoteStoreRestoreService.java#L136-L197), [all-shard transition](https://github.com/opensearch-project/OpenSearch/blob/3.9.0/server/src/main/java/org/opensearch/index/recovery/RemoteStoreRestoreService.java#L225-L254)

The tag also contains optional fenced automatic shard restoration, but its node-loss tests retain a separate cluster manager. Do not assume that option makes the proposed single combined-node total-loss scenario operator-free. [Automatic restoration test](https://github.com/opensearch-project/OpenSearch/blob/3.9.0/server/src/internalClusterTest/java/org/opensearch/remotestore/RemoteStoreAutoRestoreIT.java#L76-L89), [test topology](https://github.com/opensearch-project/OpenSearch/blob/3.9.0/server/src/internalClusterTest/java/org/opensearch/remotestore/RemoteStoreAutoRestoreIT.java#L163-L190)

Retain deployment settings, plugin versions, TLS/admin recovery material, repository configuration, and a reproducible IAM/keystore mechanism outside the lost disk. Remote state does not replace those prerequisites. S3 encryption/KMS configuration and decrypt access must survive instance replacement; encrypted EBS alone is insufficient. The self-managed S3 repository supports explicit SSE-S3/SSE-KMS settings. [S3 settings](https://docs.opensearch.org/latest/api-reference/snapshots/create-repository/), [credential selection](https://github.com/opensearch-project/OpenSearch/blob/3.9.0/plugins/repository-s3/src/main/java/org/opensearch/repositories/s3/S3Service.java#L421-L460)

## Snapshots, deletion, and logical rollback

Remote store preserves the current state, including legitimate but mistaken document updates/deletes. Deleting a namespace's index also removes its metadata and can trigger remote segment cleanup; remote translog generations and old metadata are cleaned up. Remote store is not a retained change journal or general undelete mechanism. [Index deletion semantics](https://docs.opensearch.org/latest/im-plugin/index-operations/), [index deletion cleanup](https://github.com/opensearch-project/OpenSearch/blob/3.9.0/server/src/main/java/org/opensearch/index/IndexService.java#L1024-L1026), [remote segment cleanup](https://github.com/opensearch-project/OpenSearch/blob/3.9.0/server/src/main/java/org/opensearch/index/store/RemoteSegmentStoreDirectory.java#L1404-L1418), [translog cleanup](https://github.com/opensearch-project/OpenSearch/blob/3.9.0/server/src/main/java/org/opensearch/index/translog/RemoteFsTranslog.java#L800-L861)

Keep the accepted hourly S3 snapshots, seven-day retention, and minimum three complete, successful, coverage-verified snapshots. Recommend a distinct snapshot repository with `remote_store_index_shallow_copy=false` and `shallow_snapshot_v2=false`. Shallow snapshots reference live remote segment objects; they are not an independent copy of those objects. [Shallow snapshots](https://docs.opensearch.org/latest/tuning-your-cluster/availability-and-recovery/remote-store/snapshot-interoperability/), [repository defaults](https://docs.opensearch.org/latest/api-reference/snapshots/create-repository/)

In the pinned implementation, the non-shallow path acquires a flushed Lucene commit and copies/reuses its files **inside the snapshot repository**. Restore removes source remote settings on a nonremote target or overrides them for a remote target. This supports an independent full-snapshot recovery candidate; verify it with source live repositories inaccessible before claiming independence. Snapshots retain only their captured shard states, not later writes or a single atomic instant across namespaces. [Full snapshot branch](https://github.com/opensearch-project/OpenSearch/blob/3.9.0/server/src/main/java/org/opensearch/snapshots/SnapshotShardsService.java#L469-L490), [snapshot file storage](https://github.com/opensearch-project/OpenSearch/blob/3.9.0/server/src/main/java/org/opensearch/repositories/blobstore/BlobStoreRepository.java#L4018-L4091), [target settings](https://github.com/opensearch-project/OpenSearch/blob/3.9.0/server/src/main/java/org/opensearch/snapshots/RestoreService.java#L784-L815), [snapshot consistency](https://docs.opensearch.org/latest/tuning-your-cluster/availability-and-recovery/snapshots/snapshot-restore/)

Closed indexes are excluded by default and current Create Snapshot documentation requires naming them explicitly. Use an exact namespace inventory, verify every expected index and shard in completed snapshots, and test closed-index full snapshot/restore on the selected version. Neither snapshot `accepted:true` nor `SUCCESS` without expected coverage satisfies the retention floor. No mandatory reopen procedure is established by this research. [Create Snapshot API](https://docs.opensearch.org/latest/api-reference/snapshots/create-snapshot/)

## Compatibility and remaining validation

Configure the new candidate with remote storage from initial creation. Although the overview describes bootstrap-only enablement, the official migration guide supports rolling conversion from document replication starting at 2.15; it is inaccurate to claim later migration is categorically impossible. That procedure is not evidence for zero-downtime migration of a lone node. [Migration guide](https://docs.opensearch.org/latest/tuning-your-cluster/availability-and-recovery/remote-store/migrating-to-remote/)

Official 3.9.0 Linux ARM64 artifacts exist. This establishes platform availability, not the proposed node's capacity or recovery speed. Zero replicas does not provide live availability during node replacement or recovery. Request-durable uploads also place S3 connectivity, authorization, and latency on the write acknowledgment path; remote metadata access is required during fresh bootstrap. No source establishes workload-specific latency, throughput, recovery time, or cost for the candidate. [ARM64 distribution](https://docs.opensearch.org/latest/install-and-configure/install-opensearch/tar/), [remote upload wait/failure behavior](https://github.com/opensearch-project/OpenSearch/blob/3.9.0/server/src/main/java/org/opensearch/index/translog/transfer/TranslogTransferManager.java#L251-L334)

Before adoption, validate on the exact release, ARM64 installation, S3 configuration, and representative namespace inventory:

- Kill the only combined data/manager node and discard all its disks immediately after recorded successful mixed bulk items, before refresh/flush/snapshot. Restore without PostgreSQL and verify IDs, terms, updates, deletes, BM25 results, and ability to write.
- Include index creation, mapping changes, index deletion, namespace isolation, and open/closed transitions; distinguish committed results and ambiguous requests. Verify the new UUID and complete index inventory.
- Inject S3 failures and latency, permission denial, and unavailable KMS access. Verify unsuccessful/ambiguous outcomes never become Knowhere readiness success, and recovery after access restoration is understood.
- Restore full snapshots with live segment/translog/state repositories inaccessible, including explicitly named closed indexes and deleted namespaces. Check snapshot coverage and preserve at least three proven complete recovery points.
- Measure both recovery targets end to end, including instance/bootstrap preparation and Knowhere lexical readiness. Treat the targets as unmet until measured; there is no PostgreSQL regeneration escape path.

No infrastructure changes, durability fault tests, or production operations were performed for this research.
