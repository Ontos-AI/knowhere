# OpenSearch coordination semantics: PostgreSQL locks, late RPCs, and cleanup

Date: 2026-11-03. Scope: design research, PostgreSQL 15 and OpenSearch **3.9.0**. No application changes, remote tests, or infrastructure changes were performed. PostgreSQL 15 documentation and the exact OpenSearch `3.9.0` source tag establish the semantics below; current OpenSearch documentation supplies API context. A proposed coordination policy is explicitly distinguished from a platform guarantee.

## Findings that constrain the design

1. Short PostgreSQL transactions can serialize admission, ownership, and publication decisions. Their locks do not extend into OpenSearch after commit.
2. An expired controller lease does not revoke an already dispatched open/close request. A lost response must remain an **unknown remote outcome**, even when a later state read shows the desired state.
3. Open/close has no caller-supplied generation precondition or execution-deduplication token in the checked API. `X-Opaque-Id` is observability metadata.
4. Delete-by-query is a conditional deletion of a search snapshot, not a fence against future matching writes. Garbage collection must revisit retired scopes after late writes.

These conclusions follow from the sources and execution paths below. They do **not** establish that current Knowhere code implements the proposed safeguards.

## PostgreSQL: brief decisions with explicit lock order

`FOR SHARE` allows concurrent shared holders while excluding modifications and stronger conflicting row locks. `FOR UPDATE` excludes all other row-lock modes on that row. Locks normally remain until transaction end. Acquire the strongest needed mode initially and acquire multiple objects in one consistent order; handle deadlock/serialization failures with bounded retries. [PostgreSQL 15 explicit locking](https://www.postgresql.org/docs/15/explicit-locking.html#LOCKING-ROWS)

**Recommended policy:** use one durable lifecycle gate per concrete tenant/index identity. An admission transaction takes that gate `FOR SHARE`, validates its admissible state, and inserts or renews its independent lease/pin record. A lifecycle transition takes the same gate `FOR UPDATE` before deciding whether admission has drained. If a path must modify the gate itself, acquire `FOR UPDATE` initially; do not let concurrent admissions upgrade shared locks. Choose and document one order, for example lifecycle gate → document → attempt/pin rows, with identifiers sorted within each class. All writers must follow that order. These are application conventions, not automatic database behavior.

At Read Committed, a locking statement can wait and return a newer row version; a subsequent statement gets a fresh snapshot. Lock the stable gate first, then read dependent leases/pins and validate ownership/state again. Do not rely on an earlier unlocked read or on the absence of child rows being protected by a parent-row lock: that protection exists only when all inserters obey the gate protocol. [PostgreSQL 15 Read Committed](https://www.postgresql.org/docs/15/transaction-iso.html#XACT-READ-COMMITTED)

`now()`, `CURRENT_TIMESTAMP`, and `transaction_timestamp()` remain fixed at transaction start. `statement_timestamp()` is fixed at statement start. `clock_timestamp()` samples actual wall time when evaluated. **After obtaining potentially contended locks**, sample `clock_timestamp()` in a subsequent validation statement for lease expiration and renewal. This prevents a pre-wait timestamp from accepting an already expired lease. A predicate evaluated before waiting is not the intended post-lock freshness check. Wall-clock timestamps are not a monotonic-clock guarantee. [PostgreSQL 15 current date/time](https://www.postgresql.org/docs/15/functions-datetime.html#FUNCTIONS-DATETIME-CURRENT)

Commit the decision/intent before OpenSearch I/O; issue the RPC outside a SQL transaction; then use another short transaction to record the result only if the durable operation identity, owner/generation, and applicable state still match. This fences stale **SQL completion/publication**, not the remote side effect. Do not keep a row lock or a SQL transaction open over network calls. PostgreSQL explicitly discourages long-held transactions/locks. [PostgreSQL 15 deadlocks](https://www.postgresql.org/docs/15/explicit-locking.html#LOCKING-DEADLOCKS)

## Open/close: acknowledgment is not cancellation

The documented `timeout` and `cluster_manager_timeout` configure waits. In the 3.9.0 open path, a cluster-state update changes the index state, acknowledgment is awaited, and active-shard waiting follows successful acknowledgment. An acknowledgment timeout produces `acknowledged=false`; that callback does not undo the state update. `shards_acknowledged=false` does not establish that the index remains closed. [Open API](https://docs.opensearch.org/latest/api-reference/index-apis/open-index/), [3.9.0 open implementation](https://github.com/opensearch-project/OpenSearch/blob/3.9.0/server/src/main/java/org/opensearch/cluster/metadata/MetadataIndexStateService.java#L931-L986), [acknowledgment callback](https://github.com/opensearch-project/OpenSearch/blob/3.9.0/server/src/main/java/org/opensearch/cluster/AckedClusterStateUpdateTask.java#L75-L95), [acknowledgment after commit](https://github.com/opensearch-project/OpenSearch/blob/3.9.0/server/src/main/java/org/opensearch/cluster/service/ClusterManagerService.java#L826-L882)

Close is a three-stage operation: install a write block, verify/drain shard operations, and submit the final CLOSE state. Its response can contain per-index failures and partial success. The checked implementation applies waits at individual stages; the API timeout must not be advertised as an end-to-end deadline after which no close effect can occur. Even an already closed no-op may return `shards_acknowledged=false`. Inspect per-index results and verify the actual state/blocks needed for the next operation. [Close API](https://docs.opensearch.org/latest/api-reference/index-apis/close-index/), [3.9.0 close workflow](https://github.com/opensearch-project/OpenSearch/blob/3.9.0/server/src/main/java/org/opensearch/cluster/metadata/MetadataIndexStateService.java#L167-L300), [two shard-verification requests](https://github.com/opensearch-project/OpenSearch/blob/3.9.0/server/src/main/java/org/opensearch/cluster/metadata/MetadataIndexStateService.java#L672-L714)

For both synchronous REST endpoints, 3.9.0 uses the ordinary node client, without the HTTP-channel cancellation wrapper. The request inheritance chain uses the default `Task`, not `CancellableTask`. Therefore a client disconnect, client deadline, or controller process crash must not be used as cancellation proof. The Tasks API explicitly says that not all tasks can be canceled. Open additionally supports asynchronous task/result retrieval; its `task_execution_timeout` is wired to the acknowledgment timeout and is not an application fencing token or rollback deadline. [Open REST handler](https://github.com/opensearch-project/OpenSearch/blob/3.9.0/server/src/main/java/org/opensearch/rest/action/admin/indices/RestOpenIndexAction.java#L76-L110), [close REST handler](https://github.com/opensearch-project/OpenSearch/blob/3.9.0/server/src/main/java/org/opensearch/rest/action/admin/indices/RestCloseIndexAction.java#L72-L85), [default task creation](https://github.com/opensearch-project/OpenSearch/blob/3.9.0/server/src/main/java/org/opensearch/tasks/TaskAwareRequest.java#L63-L68), [HTTP cancellation wrapper](https://github.com/opensearch-project/OpenSearch/blob/3.9.0/server/src/main/java/org/opensearch/rest/action/RestCancellableNodeClient.java#L57-L65), [Cancel Tasks API](https://docs.opensearch.org/latest/api-reference/tasks/cancel-tasks/)

The checked open/close request schemas and handlers expose no caller epoch compare-and-set, expected lifecycle version, or execution-idempotency token. `X-Opaque-Id` tracks tasks/callers and deprecation warnings; it does not reject a duplicate operation or an obsolete controller. Repeating the same desired state may be a no-op, but that is insufficient when an opposite operation interleaves. [Open request](https://github.com/opensearch-project/OpenSearch/blob/3.9.0/server/src/main/java/org/opensearch/action/admin/indices/open/OpenIndexRequest.java), [close request](https://github.com/opensearch-project/OpenSearch/blob/3.9.0/server/src/main/java/org/opensearch/action/admin/indices/close/CloseIndexRequest.java), [common REST headers](https://docs.opensearch.org/latest/api-reference/common-parameters/#x-opaque-id-header)

OpenSearch does internally verify that the unique closing block still exists before finalizing a close. A concurrent open can remove that block, making that particular close fail. This is not caller fencing: a delayed close that reaches the server **after** the open can install a fresh block and close the index. [3.9.0 closing-block check](https://github.com/opensearch-project/OpenSearch/blob/3.9.0/server/src/main/java/org/opensearch/cluster/metadata/MetadataIndexStateService.java#L855-L877)

### Crash counterexample and conservative recovery

Controller A commits close intent and sends close; the request is delayed. A dies or its lease expires. Controller B acquires a higher SQL generation, observes/open-checks the index, and admits a new reader. A's close then arrives and closes the index. SQL generation validation prevents A from committing a stale completion row, but cannot stop that close. A state read, finite quiet period, missing task, or successful opposite RPC alone does not prove that no delayed request remains. This is an inference from the unfenced request path, not a claim of a tested incident.

**Recommended bounded policy:** journal intent before dispatch; permit at most one outstanding lifecycle operation per concrete index; use finite call deadlines and bounded reconciliation attempts; mark lost-response/crash windows `uncertain`; keep admission and opposite lifecycle operations blocked for that identity until the exact operation is resolved and no old dispatcher can send again. A known terminal task/result can be useful evidence, but a missing task is insufficient for a request whose server acceptance is unknown. Do not automatically clear uncertainty on SQL lease expiry. If evidence cannot resolve it within the operational budget, retain the blocked state for operator recovery rather than promise bounded automatic availability. Alternatively, postpone automatic idle close. This policy can run in existing workers/request paths; it requires no additional always-on service.

The same limitation applies to expiring workload leases: expiry proves loss of application authority, not that an already dispatched OpenSearch operation has finished. Any claim that all actual remote work has drained needs an independently justified completion/termination bound. A client-side timeout alone supplies no such proof.

## Delete-by-query: repeat cleanup for late writes

Delete-by-query obtains a search snapshot, then submits conditional deletes. A new matching document arriving after the snapshot is outside that pass. An updated matching document may conflict and survive. With `conflicts=proceed`, conflicts are counted and skipped; the option does not force their deletion. Successful batches are not rolled back when a later batch fails. The 3.9.0 code attaches each hit's sequence number and primary term to its delete request and counts/optionally ignores conflict failures. [Delete-by-query API](https://docs.opensearch.org/latest/api-reference/document-apis/delete-by-query/), [conditional delete construction](https://github.com/opensearch-project/OpenSearch/blob/3.9.0/modules/reindex/src/main/java/org/opensearch/index/reindex/AsyncDeleteByQueryAction.java#L67-L74), [conflict handling](https://github.com/opensearch-project/OpenSearch/blob/3.9.0/modules/reindex/src/main/java/org/opensearch/index/reindex/AbstractAsyncBulkByScrollAction.java#L507-L515)

**Recommended policy:** retire an immutable revision/attempt scope in SQL before cleanup and prevent it from becoming published again. Address writes and deletes by exact tenant, concrete index, revision, and attempt/generation; never reuse a retired scope. Recheck ownership before each write batch and before publication, while recognizing that an already accepted batch can arrive late. Keep a durable cleanup tombstone and revisit it after failures, conflicts, delayed batches, and subsequent refresh visibility. Each run uses a bounded document/time budget and persists progress for another run. Verify with a fresh visible search/count before recording a pass as empty; neither an empty pass nor `refresh=true` prohibits later inserts. Do not delete the tombstone or assert permanent physical removal until writer termination/in-flight completion is justified. These are design requirements inferred from snapshot deletion, not additional OpenSearch guarantees.

## Validation limits

This is primary-source review only. It does not establish deployment settings, proxy retry behavior, plugin-specific behavior, task retention, a hard remote execution bound, or acceptance under controller-crash fault injection. Those remain implementation/acceptance evidence to collect before promising automatic crash recovery or physical cleanup completion.
